# GuiaIA — Cobblemon 1.8.2 + testigo Ed25519 físicamente remoto en Durán: PASS

**Fecha:** 2026-11-02. **Rama:** `main`, partida `4ef7fea`. **Resultado:** **PASS** en mundo de laboratorio aislado, código de salida 0. No es instalación productiva, autenticación Microsoft ni corte físico de Durán.

## Causa raíz comprobada del bloqueo anterior

En los primeros intentos, el proxy HTTPS de Chromebook enviaba al testigo el HTTP `Host: durn.taild703f5.ts.net` (cabecera conservada por Tailscale Serve), pese a que el testigo `qa_checkpoint_witness.js` exige **simultáneamente** conexión TCP de loopback y `Host` comenzando por `127.0.0.1:`. En consecuencia, el testigo respondía HTTP 403 **antes de verificar las firmas**. Esto se demostró colocando temporalmente un inspector de cabeceras estrictamente QA en el destino de Serve: registró únicamente `host`, `remoteAddress` y método, sin cuerpo, firmas, claves ni UUID. El inspector vio `remote=127.0.0.1` y `host=durn.taild703f5.ts.net`. Por tanto, el timeout fue una hipótesis equivocada sobre la causa principal de ese intento.

La corrección mínima se efectuó **solo en `companion/qa_physical_witness_proxy.js`**: el proxy sigue conectándose por HTTPS con SNI `durn.taild703f5.ts.net`, exige `rejectUnauthorized:true` y fija **solo la cabecera HTTP Host** de la solicitud interior a `127.0.0.1:<puerto testigo>`. El puerto debe declararse con `GUIAIA_QA_REMOTE_WITNESS_LOOPBACK_PORT` y pasar validación estricta (número canónico 1024–65535). El proxy no añade firmas, no fabrica recibos y no modifica el algoritmo de checkpoint. No se alteraron ni el límite de **1.500 ms** del cliente de autoridad ni el de **1.250 ms** del proxy HTTPS; no se aflojó la identidad Ed25519 ni CAS. El inspector volvió a comprobar `host=127.0.0.1:<puerto configurado>` y `remote=127.0.0.1` antes del ensayo real.
